# ADR-010: Device App Inventory + Postcondition → Evidence Seam (Phase 5A)
**Status**: ACCEPTED | **Date**: 2026-08-31

## Context

Phase 4.5 proved a verified Android action can reach `VERIFIED` on the
`/api/agent/intent` path (the run's own envelopes). But on the **normal chat
path** there was still no canonical Phase 3 Evidence for Android actions: a
ToolResult carried device postconditions in `data`, and the verifier could
read them only if the mixers/recorders happened to forward them. Nothing
converted them into the ledger the response verifier grades, so a verified
Android action on chat stayed capped at `INFERRED`.

Separately, there is no general way to answer device-state questions that
need the plain truth about what is installed — "is WhatsApp installed?",
"what apps do I have?" — with a fresh, timestamped, privacy-safe answer. The
Phase 5 audit ranked installed-app inventory as the smallest safe read-only
addition.

## Decision

Add exactly one read-only capability and tool, plus a deterministic evidence
seam. No caching, no event-driven updates, no second model, no new dependency.
Reuse the existing provider / ToolResult / Evidence / verifier primitives.

### Capability and tool

- **Capability** `android.app_inventory` (tool `android.list_apps`),
  registered through the canonical `core/capabilities/factory.py` mechanism
  with `required_dependencies=["android.companion"]`, the same accessibility
  permission gate, and the same health/availability model as the other 14
  Android capabilities. Registration alone never makes it claim availability:
  availability stays a live runtime fact.
- **Tool** `AndroidListApps` in `tools/providers/android_provider.py`,
  `ToolRisk.SAFE`, `SideEffect.READ_ONLY`, structured output, schema-validated
  with `observed_at` required and `device_id` when known.
- **Bridge normalization** `normalise_device_report` validates the wire shape
  for `android.list_apps`: `packages` must be a list and `observed_at` must be
  present. Malformed inventory → `EXECUTION_FAILED`, never success, never
  coerced. UNKNOWN stays UNKNOWN.
### Device half and evidence seam

- **Device half** (`android/.../AppInventory.kt`): `PackageManager` behind a
  narrow `PackageSource` seam (the same trick `AccessibilityToolDispatcher`
  uses). Pure `AppInventory.collect` is JVM-testable off-device and
  deterministic (name-sorted, de-duplicated, launchable entries kept).
  Launchability comes from the MAIN/LAUNCHER query only (the manifest already
  declares it for `open_app`); `QUERY_ALL_PACKAGES` is **not** added. The
  observation payload and content hash carry counts and a SHA-256 only —
  never package names, labels, or the list itself.
- **Evidence integration** (`_evidence_from_report` / `tool_result_from_report`
  in `android_provider.py`): a device postcondition with an explicit boolean
  `verified` becomes canonical `EvidenceKind.POSTCONDITION` evidence;
  `verified=true` grounds a VERIFIED action claim, `verified=false` stays
  failed (CONTRADICTED by the verifier, never success), and a missing or
  malformed postcondition produces no verification evidence. An
  `app_inventory` observation becomes `EvidenceKind.OBSERVATION` evidence —
  current device state, deliberately **not** promoted to persistent memory.
- **No cache by default**: every `list_apps` re-enumerates and stamps a fresh
  `observed_at`; the only way a stale list cannot be served as current state
  is for there to be no stored list at all.

## Semantics: existence ≠ availability ≠ fresh proof

Registered capability and declared tool are never proof that "X is installed".
Only a fresh inventory observation (OBSERVATION evidence) can ground an
installed-app claim. Old memory alone, semantic similarity alone, and
capability/tool existence alone are all insufficient.

## Privacy boundary

Package names and labels never enter diagnostics; the full inventory is never
logged; inventory content never rides in generic trace metadata. The OBSERVATION
evidence the server reads carries counts and a content hash only. Inventory is a
current device observation, not user memory.

## Failure UX

`ToolError`/`ToolStatus` semantics are used throughout. Inventory unavailable →
"could not be retrieved"; permission denied → "access is unavailable"; timeout →
"the device did not respond in time"; UNKNOWN → "the current state could not be
verified". No generic "I cannot continue." path is introduced.

## Offline verifiability

Everything except the real `PackageManager` call is verified offline: the
Python suite uses a loopback/scripted `DeviceBridge`, and the Android JVM tests
drive the pure `AppInventory` through a `PackageSource` fake. No physical device
is required, and none is claimed. Live device verification is a separate,
explicitly-flagged step and remains `IMPLEMENTED BUT NOT VERIFIED`.
## Alternatives Considered

- **Cache enumeration behind a TTL.** Rejected: no measurement shows a
  performance problem; a cache would add a way for a stale list to be served
  as current, which the freshness contract forbids. Revisit only if a real
  device measurement justifies it.
- **Background / event-driven inventory.** Rejected: violates "observe on
  demand"; complexity with no demonstrated offline need.
- **Grant `QUERY_ALL_PACKAGES`.** Rejected: answers far more than "which apps
  are here" and needs a Play policy declaration; the existing MAIN/LAUNCHER
  query is already granted and sufficient for launchability.
- **A parallel tool/provider framework for inventory.** Rejected: reuses the
  existing `Tool`/`ToolResult`/`Evidence` machinery exactly as intended.
- **A second model call to grade device state.** Rejected (unchanged from
  ADR-009): deterministic, no new model.

## Consequences

- The chat-path verifier can now reach `VERIFIED` for a verified Android action
  (postcondition → POSTCONDITION Evidence in the ledger).
- Installed-app claims require fresh OBSERVATION evidence; everything else is
  UNKNOWN/INFERRED.
- Privacy is enforceable: package data is structurally kept out of the trace.
- No regression to Phase 4/4.5 adversarial rules (verified=true → VERIFIED;
  verified=false / missing / malformed → never VERIFIED).
- Limitation: visibility filtering means the device reports the installed set
  *it can see*; absence of an entry is never reported as "not installed".

### Live verification 2026-09-05

Executed verify-only, on device, with no architecture change and no install.

- `android.list_apps` SUCCESS in **3.80 s**: 277 packages, `count=277`, fresh
  `observed_at` (23.9 s old at read), `device_id`,
  `source="android.package_manager"`, `postcondition=null`,
  `evidence=VERIFIED`, `side_effect=READ_ONLY`. 88 launchable, 269 enabled, 0
  duplicates. The no-cache freshness contract holds live, and performance on a
  real handset is now a measured number rather than UNKNOWN.
- `android.app_inventory` reported `AVAILABLE` by `/api/capabilities` over a
  live companion heartbeat, alongside the other 14 (15 total),
  `authorization=granted`, `health=healthy`.
- Privacy boundary holds live: the observation payload carries only
  `{count, launchable_count, source}` plus a SHA-256 content hash, and a sweep
  of all 10,567 lines of `logs/diagnostics.jsonl` found 0 inventory package
  names or labels.
- The postcondition → Evidence seam is proven live in both directions:
  `{"verified": true}` → `EvidenceKind.POSTCONDITION` → `ClaimState.VERIFIED`
  (decision PASS); `{"verified": false}` → CONTRADICTED with the false claim
  repaired away, for a read-only check (`android.verify`) and for a mutating
  tool (`android.launch_app`). An `app_inventory` observation is `OBSERVATION`
  and never `POSTCONDITION`; a bare `{"ok": true}` produces no Evidence and
  grades INFERRED.
- Regression: full suite unchanged at `3489 / 2 / 1 / 5`, the 5 being exactly
  the pre-existing settings-restart set.

Still not verified: a *verified* postcondition on a *mutating* action (the
screen was off and locked, so `android.launch_app` correctly declined to
confirm a state change). Unrelated to this ADR's inventory contract.
