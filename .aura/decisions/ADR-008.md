# ADR-008: Structured Tool Output Contract
**Status**: ACCEPTED | **Date**: 2026-08-29

## Context

The AURA 2.0 contract (Phase 3) requires the tool system to be machine-readable
end to end. Before this change, a tool result was a bool plus two free-form
strings invented at each call site. The reasoning layer could not distinguish
"the phone is not connected" from "the tool crashed", or "we stopped waiting"
from "it definitely did not happen" — different sentences to a user and
different decisions to a runtime. Provider-level function-calling failures
("No cloud provider is configured or supports function calling") could
collapse into a generic task-aborted message and invite failover retries
against providers that could never serve the request.

Phase 1 already made the *provider-registry* side typed
(`CapabilityUnavailableError`, capability-first routing). This ADR makes the
*tool-result* side typed, device-independently, without rebuilding the
existing tool infrastructure.

## Decision

Four vocabularies live in `tools/outcome.py`, deliberately separate:

- **`ToolStatus`** — did it happen. Nine values:
  `SUCCESS` (completed, nothing contradicts it; alone it is NOT proof of a
  world change), `FAILED` (attempted and failed), `PARTIAL` (some work done,
  whole operation did not), `DENIED` (policy/permission/confirmation
  prevented execution, nothing ran), `UNAVAILABLE` (capability/tool/provider/
  device absent right now; always safe to retry), `INVALID_ARGUMENTS`
  (failed validation before execution), `TIMEOUT` (exceeded its allowed
  time), `CANCELLED`, `UNKNOWN` (outcome cannot be established safely).
- **`ToolError`** — why it did not happen. `code`, `message`, `provider`,
  `capability`; `category` is DERIVED from `code` via
  `category_for_code` (`ToolErrorCategory`: VALIDATION / PERMISSION / POLICY /
  CAPABILITY / PROVIDER / NETWORK / TIMEOUT / EXECUTION / INTERNAL / UNKNOWN).
  A capability failure is a CAPABILITY error, never a PROVIDER error, so a
  missing capability can never be retried against an incapable provider.
- **`Evidence`** — how we know it happened. `kind` (POSTCONDITION /
  OBSERVATION / RECEIPT / RETURN_VALUE), `source`, a tri-state `verified`
  (True passed / False failed / None not checked), `timestamp`, `reference`.
  `None` is not a weaker True; never construct evidence for a check that did
  not happen. `evidence_state()` summarises NONE / UNVERIFIED / VERIFIED /
  CONTRADICTED.
- **`SideEffect`** — what re-running costs: READ_ONLY / IDEMPOTENT /
  NON_IDEMPOTENT / UNKNOWN. Conflating this with `ToolRisk` (the permission
  question) is exactly the bug this ADR removes: a read-only file read was
  previously treated as a mutation needing verification.
Invariants enforced mechanically, not merely documented:

1. **UNKNOWN is never success.** `ToolResult.ok` is reconciled FROM `status`
   in `__post_init__`; only SUCCESS is truthy. No construction path can
   produce a truthy UNKNOWN, and `serialize_for_model` appends an explicit
   "OUTCOME UNVERIFIED … do not claim it succeeded" line.
2. **Retryability is derived, never asserted.** `retryability_of(status,
   side_effect)` → SAFE / NOT_SAFE / UNKNOWN. A side-effecting UNKNOWN is
   never safe to retry, so `send_sms` cannot be doubled by an auto-retry.
3. **Malformed output is not success.** `validate_output()` checks a tool's
   declared `output_schema` (type at root, required/property types one level
   deep, items for arrays — microseconds, no dependency); a mismatch
   downgrades the result to UNKNOWN, never silently accepted.
4. **Capability failures stay distinct.** `CODE_CAPABILITY_UNAVAILABLE`
   maps to the CAPABILITY category and UNAVAILABLE status, distinguishable
   from a provider execution failure — `CapabilityUnavailableError` is NOT
   a `ProviderUnavailableError`.

`ToolResult` (tools/base.py) keeps its original fields and adds `status`,
`error_code`, `evidence`, `execution_id`, `started_at`, `completed_at`,
`side_effect`. The executor stamps identity, derives evidence, folds the
contract keys into `data` for envelope callers, and emits one
`tool_execution` diagnostics line per execution (identity, status, duration,
retryability, evidence state — never arguments or content).

The model-facing rendering is `serialize_for_model()` (tools/base.py): fixed
`STATUS:` / `TOOL:` / `EVIDENCE:` / `RETRY:` lines, then `OUTCOME:` (the
sentence models are already calibrated to) and `ERROR: code/category` for
failures. No arguments, no timestamps, no execution internals in the prompt.
`brain/conversation.py._render_result` routes any `ToolResult` through it;
foreign duck-typed results keep the legacy prose.

The registry (`tools/registry.py`) exposes `definitions()` — one canonical
machine-readable definition per tool (name, description, input/output schema,
side_effect, risk, version, capability) — and `export_mcp()`, which renders
the standards `tools/list` shape (name, description, inputSchema). This is
**MCP-adapted** (conceptual `tools/list`/`tools/call` compatible via the
OpenAI function shape both already share), not a full MCP server, and it is
NOT a hard runtime dependency. Tool metadata stays in one place — the tool
class — and is rendered; there is deliberately no static YAML registry file
that could drift from the tools it describes.

## Alternatives Considered

- **A static YAML/JSON registry file.** Rejected: availability and policy are
  live facts; a snapshot that pre-joined them lies the moment either changes.
  Code-derived, in-process definitions keep one source of truth.
- **A full JSON Schema library for validation.** Rejected: the runtime only
  needs its own tools' shapes; the subset validator covers the realistic
  contract and costs microseconds.
- **Making a real MCP server a runtime dependency.** Rejected: nothing in the
  architecture consumes it today, and the contract forbids adding MCP merely
  for branding. The export adapter exists; a server can wrap it later.

## Rejected Alternatives & Rationale

- **Letting each tool write its own status/error prose.** Rejected: that is
  the exact free-form failure mode this contract removes.
- **Auto-retrying on UNKNOWN.** Rejected: UNKNOWN must never be converted to
  SUCCESS, and side-effecting UNKNOWN results must never be repeated.
- **Reusing `ToolRisk` for retry safety.** Rejected: permission cost and
  retry safety are different questions; conflating them re-created the
  phantom-verification bug.
- **Single "generic failed" taxonomy.** Rejected: loses the
  PARTIAL/DENIED/UNAVAILABLE/UNKNOWN distinctions the runtime must branch on.

## Consequences

- The reasoning layer can now branch on `status`, `error_category`,
  `evidence_state` and `retryability` without parsing prose, in the prompt
  (`serialize_for_model`) and in code (`ToolResult` / registry).
- Tool authors declare `output_schema` and `side_effect` on the class; the
  honest default is undeclared (validation skipped) / UNKNOWN (not retry-safe).
- Human-confirmation, permission and capability gates are untouched and
  remain as strict as before; nothing here weakens a safety gate.
- Every existing tool that returns plain strings still works — the legacy
  contact surface (`ok`/`error`/`output`) is preserved.
- `UNKNOWN` may never be reported as a success; the final response must say
  completion could not be verified.
- One new per-execution diagnostics line (identity + status + duration +
  retryability + evidence state; no secrets, no content). Trace failure never
  breaks execution.

- core/trace.py consumers (per-execution diagnostics line)
