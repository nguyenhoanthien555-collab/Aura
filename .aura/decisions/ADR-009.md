# ADR-009: Response-Level Claim → Evidence Verification (Phase 4)
**Status**: ACCEPTED | **Date**: 2026-08-30

## Context

Phase 3 made tool *results* typed; the reasoning layer could branch on
status, evidence and retryability. What remained missing (audit gap 6) was
a boundary over **free-form chat**: nothing checked the generated reply
against what the runtime actually established this turn. A model could
say "I sent the email" after `email.send` returned FAILED, or "your phone
has WhatsApp installed" from stale memory, and the reply was delivered
verbatim.

The AURA 2.0 contract (Phase 4) requires a deterministic claim → evidence
verifier: five claim states, typed claim classes, a request-scoped
evidence ledger, hard action-claim rules, memory/capability/current-state
strictness, minimal repair, contradiction handling, a hallucination
taxonomy and privacy-safe diagnostics — with NO second model call, and
without making ordinary general-knowledge conversation unusable.

## Decision

`brain/verify/` implements the boundary as six small modules, all
deterministic table lookups, none of which import a model:

- **`status.py`** — `ClaimState`: VERIFIED / SUPPORTED / INFERRED /
  UNKNOWN / CONTRADICTED (never a boolean; never upgraded by confident
  phrasing). `VerifierDecision`: PASS / REPAIR / MARK_UNCERTAIN /
  ASK_CLARIFICATION / REFUSE_UNSUPPORTED_CLAIM.
- **`claims.py`** — `extract_claims`: deterministic sentence splitting
  (abbreviation/initial-aware) and a fixed pattern table (EN/VI) classifying
  ACTION / FACTUAL / CAPABILITY / TEMPORAL / NUMERICAL / IDENTITY /
  MEMORY_DERIVED / GENERAL. The `_WORLD_OBJECT` closed vocabulary is the
  scope gate: a claim that names nothing in the user's world is recorded
  but never grounded or rewritten — this is what keeps "Python is
  dynamically typed" natural while "I checked your calendar" is strict.
- **`ledger.py`** — `EvidenceLedger`, request-scoped, holding
  `ToolEvidence` (wrapping the canonical Phase 3 `Evidence`/`ToolStatus`
  — never duplicated) and `MemoryEvidence` (provenance, confidence,
  recency, conflict). The model's own text is never admissible evidence
  for its own claims.
- **`rules.py`** — `verify_claim`: maps evidence state to claim state.
  Hard action boundary: SUCCESS + verified postcondition → VERIFIED;
  SUCCESS + RETURN_VALUE-only → INFERRED (never VERIFIED); UNKNOWN /
  FAILED / DENIED / UNAVAILABLE can never ground a success claim, and
  FAILED/DENIED/UNAVAILABLE mark it CONTRADICTED. PARTIAL grounds only
  its verified portion.
- **`repair.py`** — minimal repair: only the offending sentence is
  replaced, never more; repairs only ever move a claim DOWN in certainty
  (hedge "I can't verify...", attribute memory with "From what I
  remember..."), and GENERAL/ordinary-knowledge sentences are untouched.
  Nothing is invented.
- **`verify.py`** — `ResponseVerifier.verify(text, ledger)` ties it
  together, never raises, emits one privacy-safe `verifier` trace line
  (counts + decision + latency, never text), and chooses the decision
  card (REPAIR > REFUSE > ASK_CLARIFICATION > MARK_UNCERTAIN > PASS).



## Phase 4.5 addendum (2026-08-30): runtime integration hardening

A Phase 4.5 audit traced every final-response path. One user-visible
path returned an unverified reply, and the integration matrix exposed
two deterministic rule gaps. Fixes, all within the existing architecture:

1. **`POST /api/agent/intent` now verifies its reply.**
   `brain/verify/ledger.py::ledger_from_transcript` converts the run
   transcript's `role="tool"` envelope messages into ledger evidence
   (ok/error-code/postcondition → ToolStatus + tri-state Evidence,
   deterministic; unparseable or non-dict envelopes are skipped, never
   guessed); `brain/verify/verify.py::verify_run_reply` runs the
   standard ResponseVerifier over the reply; `server/routes/agent.py`
   returns the repaired reply plus a metadata-only `verifier` summary,
   gated by `response.verify.enabled` (default on) and
   failure-tolerant (a grounding outage never costs the answer).
2. **SUCCESS + postcondition verified=False is CONTRADICTED**, not
   INFERRED (`brain/verify/rules.py::_grade_success`). A failed check
   is a positive finding; a success envelope wrapping a failed check is
   still a failure.
3. **A user-world FACTUAL claim graded INFERRED is qualified**, never
   delivered as bare fact (`brain/verify/repair.py::repair_claims`).

The deferred device-driven step path (`/api/agent/step`) returns
directives and run snapshots, not final prose; the run's final answer
reaches users through `/intent` (inline) or the device UI (deferred),
and only the server-owned inline surface could be verified here. The
deferred surface is BLOCKED on the disconnected device and recorded as
such, not silently claimed.

No architectural change, no new dependency, no second model call. All
Phase 4 invariants (A–J of the Phase 4.5 contract) are enforced by the
existing rules and now proven end to end in
`tests/test_phase45_integration.py`.



**Integration** (minimal, no architecture change): `ConversationManager`
builds the ledger per turn when a verifier is injected, records every tool
outcome and recalled memory line into it, and runs `_verify_final` on the
styled text before delivery — on both the `chat` and `chat_stream` paths.
The launcher's composition root builds the verifier from
`response.verify` config (`enabled`, `repair`); `enabled: false` restores
the exact pre-Phase-4 pipeline.

**Streaming** (honest boundary): fragments go out raw — that is the
existing architecture — so a false claim can momentarily reach a UI. The
authoritative final text is the repaired one, delivered in
`StreamFinishedEvent` (which carries the verifier summary) for the UI to
replace its buffer with. This is NOT "verified streaming"; it is the
safest feasible boundary without retracting delivered tokens. The
streaming path offers no tools, so no evidence-gathering turn can act
there.

## Alternatives Considered

- **A second model call to judge the reply.** Rejected by the contract:
  non-deterministic, slow, and it moves the trust boundary rather than
  closing it.
- **Buffering the whole stream before delivery.** Rejected: costs
  latency for protection the fragment path rarely needs (no tools run
  there); the finished-event replacement is documented and observable.
- **Verifying every sentence including general knowledge.** Rejected:
  hedging "Python is dynamically typed" makes normal chat unusable; the
  world-object scope gate achieves strictness only where evidence exists.

## Consequences

- A generated reply can no longer claim a side effect succeeded on
  UNKNOWN/FAILED/DENIED/UNAVAILABLE evidence; it is repaired or refused.
- Confident phrasing ("100% confirmed") adds no certainty; state comes
  only from the ledger and live capability registry.
- Old/low-confidence memory is attributed, not asserted; conflicting
  memories surface as UNKNOWN/ASK_CLARIFICATION, never a picked side.
- Capability claims are checked against the live registry — an
  unavailable capability cannot be claimed available.
- Diagnostics stay metadata-only (claim/state counts, decision, latency).
- Limitations: deterministic extraction cannot parse arbitrary prose;
  unclassifiable claims stay GENERAL/UNCLASSIFIED rather than guessed.
  Fragments stream raw (see above). Detection is imperfect BY DESIGN —
  this reduces overclaiming; it does not eliminate hallucinations.
