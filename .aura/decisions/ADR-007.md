# ADR-007: Hybrid Semantic Memory (lexical preserved)
**Status**: ACCEPTED | **Date**: 2026-08-29

## Context

The AURA 2.0 contract (Phase 2) asks for vector recall. The codebase had a
documented, deliberate decision the other way: `docs/IMPLEMENTATION_STATUS.md`
recorded recall as lexical token overlap with "no embedding model and no vector
store anywhere in this codebase". Phase 0's audit surfaced that contradiction
rather than resolving it silently, and human review settled it: semantic recall
is added as a SECOND mechanism beside the lexical one, which is preserved.

The pressure this creates is worth naming. Retrieval that "usually finds
something" is worse than retrieval that finds nothing, because a fabricated or
mis-scoped memory reaches the prompt as though it were evidence. So every
decision below is biased toward failing closed.

## Decision

Semantic recall sits at the `Retriever` seam `memory/retrieval.py` already
documents. `KeywordRetriever` and `RankedRetriever` are untouched.

- **Provider abstraction** (`memory/embeddings.py`): `EmbeddingProvider`
  protocol with `HashingEmbeddingProvider` (LOCAL, stdlib-only n-gram hashing),
  `OllamaEmbeddingProvider` (LOCAL), `RemoteEmbeddingProvider` (REMOTE).
  Metadata (provider, model, dimensions, version, locality) travels with every
  vector.
- **Storage**: one `SemanticVector` table in the existing SQLite database.
  Float32 blobs via stdlib `array`; cosine runs in process over the same
  bounded candidate pool the lexical ranker uses. No vector database, no numpy,
  no new dependency.
- **Versioning**: vectors are comparable only when provider, model, dimensions
  and version all match. A model change makes old rows stale — reported, not
  silently mixed — and semantic recall stays unavailable until a reindex.
- **Fusion**: Reciprocal Rank Fusion (k=60), chosen because the two inputs live
  in different score spaces (lexical overlap vs cosine) and no normalization
  across them existed to reuse. `memory.semantic.weight` (default 0.5) tilts
  the split; 0.5 scales both halves equally, so the default orders results
  exactly as unweighted RRF did.
- **Similarity floor**: declared by the PROVIDER, not by the retriever, because
  the useful cutoff is a property of the embedding space. Hashing declares
  0.24, MEASURED as the knee of the benchmark sweep. Model-backed providers
  declare a conservative, explicitly UNMEASURED 0.05.
- **Degradation**: provider unavailable / timeout / malformed / stale → semantic
  returns empty with a reason, hybrid serves lexical. Both failing returns an
  explicit empty, never a fabricated line. Retrieval never raises into a turn.
- **Indexing**: happens after the row commits and can never undo it. Statuses
  indexed / failed / skipped / stale are observable via
  `SemanticIndexer.status()` and the Phase 1 diagnostics trace.
- **Deletion**: semantic candidates are fetched by inner join to the live
  episodic row, so an orphaned vector is structurally unreturnable. A deleted
  memory cannot be resurrected by a stale vector.
- **Privacy**: a REMOTE provider refuses to embed unless
  `memory.semantic.allow_remote` is explicitly true — the exfiltration boundary
  is in the provider, not the caller. Diagnostics carry ids, counts, latency
  and reasons; never memory content, never vectors, never credentials.
- **Configuration**: `memory.semantic.*` in the existing config system.
  Default OFF, and off is a complete configuration. Startup never fails because
  embeddings are unavailable.

## Alternatives Considered

- **A vector database (FAISS / Chroma / sqlite-vss).** Rejected: the candidate
  pool is already bounded by `retrieval_scope`, so cosine over a few hundred
  vectors in process is fast enough, and one database keeps backup, deletion
  and Android/Render portability honest.
- **Weighted score fusion instead of RRF.** Rejected for now: it needs a
  normalization across two unlike score spaces, and inventing one untested was
  explicitly out of bounds. RRF uses rank position, the one scale both share.
- **Replacing lexical retrieval with semantic.** Rejected: the benchmark shows
  the hashing space returns noise on queries with no answer, where lexical
  correctly returns nothing. The two fail differently, which is the argument
  for keeping both.
- **One shared `min_similarity` constant.** Rejected: hashed n-grams collide
  and score everything above zero; a trained model separates cleanly. One
  constant would be wrong for at least one provider.

## Rejected Alternatives & Rationale

Making semantic retrieval a runtime dependency, or letting an embedding failure
fail a turn — both contradict invariants B, C, D and L. Also rejected: picking
a similarity floor by intuition. The floor shipped here is the measured knee of
a sweep that stayed in the benchmark precisely so the number can be re-derived
rather than trusted.

## Consequences

- Memory can operate indefinitely in lexical-only mode, which is the default.
- A model swap is detectable and non-destructive; the cost is an explicit
  reindex before semantic recall resumes.
- The hashing provider's honest limit — n-gram overlap, not paraphrase
  understanding — is documented in code, and the benchmark shows exactly where
  it costs precision.
- The measured floor (0.24) comes from a ten-memory fixture. That is a small
  measurement and is labelled as one; a real provider needs its own sweep.
